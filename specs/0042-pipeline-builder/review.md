# Build Review: Pipeline Builder

- **Spec:** 0042-pipeline-builder (`spec.md`, `plan.md`, `tasks.md`)
- **Status:** Approved — build completed
- **Reviewed by:** Josh
- **Date:** 2026-08-12

> A point-in-time record of the scoping review held **before** this spec was
> built: what the codebase already provided, which alternatives were weighed,
> and the one decision that was escalated. It is deliberately *not* maintained
> in step with the implementation — `spec.md` and `plan.md` are the living
> documents. Keep this as the record of why the build was shaped this way.

## Why this was built

`agents/data_engineering/pipeline_builder/` had shipped as an agent contract
since the `0019` group build-out — "compile a source→transform→sink intent
into a reviewable DAG with contracts, schedules, retries, tests, ownership,
and a deployment plan" — but had no runtime. It was one of three remaining
`P1` backlog items and the one that composed most cleanly with work already
shipped.

A second reason carried equal weight: `hooks/stages/pipeline-contract-check.sh`
had never validated anything, because nothing in the repository had ever
produced the artifact it scans for. That is the same gap spec `0039` closed for
data contracts.

## What the codebase already provided

Four findings from reading the relevant files before designing anything. Each
one *removed* something from this spec's scope.

| # | Finding | Effect on scope |
| --- | --- | --- |
| 1 | The agent is contract-only — four files, no runtime. | Confirms a real gap rather than a duplicate. |
| 2 | `pipeline-contract-check.sh` scans for `*pipeline_manifest*.md` and checks six themes, but no manifest exists anywhere, so every run reports "No pipeline manifest artifact detected." | Makes emitting a manifest a primary goal, not a nicety. |
| 3 | `0011` (`data_pipeline.py`) owns execution entirely — `Pipeline`, `Step`, `DataContract`, `run`, `backfill`, `RunManifest`, plus a toposort that already rejects cycles, unknown dependencies, and duplicate step names at construction. | Removes all graph and execution logic from scope; the module composes `0011` instead. |
| 4 | `instructions/pipeline_engineering.md` already carries an eight-point contract and an eight-item checklist. | The readiness rubric is encoded, not invented. |

## Shape agreed

A design-time compiler, reviewer, and renderer — explicitly **not** a second
runtime. Four functions, with a real dependency structure between them:

```text
review_readiness ──→ compile_intent ──┬──→ render_pipeline_manifest
                                      └──→ to_pipeline   (handoff edge → 0011)
```

Full component contracts, the constitution check, and the traceability matrix
live in `plan.md`. The honest-reporting boundary — that the module reviews
*declarations*, never implementations, and that idempotency and test coverage
are claims until `0011` exercises them — is `spec.md`'s `REQ-004` and
`RISK-001`.

## Alternatives weighed

Recorded here because the reasoning is easy to lose once the code exists;
`plan.md` carries the same table as the living version.

| Decision | Chosen | Rejected | Why |
| --- | --- | --- | --- |
| DAG validation | Construct a throwaway `0011` `Pipeline` with placeholder step bodies | A toposort inside this module | A second implementation could drift from `0011`'s and disagree about what a valid pipeline is — the one thing a build-time checker must never do. |
| Graph errors | Returned as blocking findings | Raised out of `compile_intent` | A design review wants every problem at once; raising on the first structural error hides the readiness findings behind it. |
| Manifest sections | The template's six, plus a disclosed `Readiness` seventh | Exactly six | The template has nowhere to record review findings; omitting them would make any manifest look clean regardless of its state. |
| DAG rendering | Per-step dependencies plus an execution-order line | The template's `a -> b -> c` chain | A topological order joined by arrows implies edges that may not exist. The worked example has two independent sources feeding one transform, which no chain can represent honestly. |

## Decision escalated

**Should a rendered example manifest be committed at
`specs/0042-pipeline-builder/pipeline_manifest.md`?**

- **Commit it.** The dormant `pipeline-contract` gate fires on real content for
  the first time, and the module is demonstrated end to end. Cost: a permanent
  file the gate scans from then on, which must keep passing.
- **Tests only.** Gate compatibility verified in the suite, nothing new
  committed — spec `0039`'s precedent for data contracts.

**Outcome: commit it**, approved explicitly. The standing cost is recorded as
`RISK-003` in `spec.md`; because the file is generated by
`render_pipeline_manifest`, regenerating it after a template change is a
reproduction rather than a hand edit.

## Scope held out

Recorded so a later reader does not mistake these for oversights — the full
list with rationale is `spec.md`'s Non-Goals.

- Execution (`0011` owns it), and code generation of step implementations.
- Schedule *semantics* — presence is checked; parsing cron would be false
  precision about a field this module cannot execute.
- Deployment logic — captured as declared metadata, handed off to
  `agents/data_engineering/pipeline_deployment/`, a separate `P1` item.
- Row-level contract validation — that is `0011`'s `DataContract.validate` and
  `0039`'s `validate_ingestion`.

## Outcome

Built as agreed. Twelve acceptance criteria, ten covered by
`tests/test_pipeline_builder.py` and two by direct gate and catalog inspection;
`pipeline-contract` now reports six checks passing against the committed
example. One deviation from the reviewed plan — the DAG rendering, in the
alternatives table above — was made during the build and recorded in `plan.md`
rather than carried silently.
