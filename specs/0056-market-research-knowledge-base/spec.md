# Spec: Market Research Knowledge Base

- **ID:** 0056-market-research-knowledge-base
- **Status:** Draft
- **Author:** QuantSmith
- **Approver:** TBD
- **Last updated:** 2026-08-22

> WHAT and WHY only. No implementation detail — that belongs in `plan.md`.

## Problem & Context

QuantSmith needs a governed market-research knowledge base where users can store,
curate, retrieve, and cite asset-class research and market color written by users,
generated by agents, produced by the firm, or received from approved external
managers and research providers. The decision this supports is whether the
existing knowledge-base/MCP layer can scale from repo-local workflow memory into
a deployable, firm-aware research platform without mixing confidential content
into the SDK repository.

Research question: what did the user, team, firm, or approved external source
believe about a market, asset class, security, regime, or strategy at a point in
time?

Engineering requirement: expose market research through the same knowledge-base
MCP interface used by other QuantSmith knowledge domains, while allowing separate
storage backends and stronger governance under that shared interface.

## Goals

- Preserve one knowledge retrieval interface for agents and users, including
  `knowledge://...` resource identifiers and MCP query tools.
- Store market color and research outside the SDK repository in governed,
  provider-appropriate backing stores.
- Support asset-class, source-type, entity, instrument, strategy, date, and
  access-level metadata so retrieval is precise and auditable.
- Enforce provenance, entitlement, citation, freshness, and point-in-time
  controls before an answer is composed.
- Make user-authored research, firm research, fund-manager materials, sell-side
  research, generated notes, and meeting/transcript-derived notes first-class
  knowledge items with different governance rules.
- Support explicitly tagged email market color as a source while avoiding broad
  inbox scanning or unreviewed mailbox ingestion.

## Non-Goals

- This spec does not build a research authoring editor, CRM, or document
  management system.
- This spec does not commit real firm, client, fund-manager, MNPI, or licensed
  third-party research content to this repository.
- This spec does not replace `0002` workflow memory or `0048` workflow memory
  runtime. Workflow memory remains the store for operational lessons about data,
  schemas, runs, and model behavior.
- This spec does not grant access to third-party research without a separately
  approved entitlement model.
- This spec does not produce trading recommendations without downstream
  research, risk, compliance, and portfolio review workflows.
- This spec does not scan an entire inbox by keyword or infer that untagged
  personal, operational, client, or vendor email is market research.

## Requirements

| ID | Requirement | Priority |
| --- | --- | --- |
| REQ-001 | The system shall represent user-authored, agent-generated, firm-authored, fund-manager, sell-side, and other approved external research as market-research knowledge items. | must |
| REQ-002 | The system shall expose market-research retrieval through the same knowledge-base MCP interface and `knowledge://...` namespace used by other QuantSmith knowledge domains. | must |
| REQ-003 | The system shall allow market-research content to live in separate governed storage backends while presenting a single MCP retrieval surface. | must |
| REQ-004 | The system shall attach required provenance to every item: source, author or publisher, source type, publication date, ingestion date, version or content hash, license/entitlement class, and owning domain. | must |
| REQ-005 | The system shall classify each item by asset class, market, entity/security/instrument when available, strategy/theme, geography, currency, source type, confidentiality, and freshness policy. | must |
| REQ-006 | The system shall enforce access level, entitlement, and information-barrier checks before retrieval and before answer composition. | must |
| REQ-007 | The system shall support point-in-time retrieval using publication date, effective date when supplied, ingestion date, supersession status, and an explicit `as_of` parameter. | must |
| REQ-008 | The system shall return cited passages or cited item summaries, never unsupported prose, for research-backed answers. | must |
| REQ-009 | The system shall distinguish facts, sourced market color, author opinion, generated synthesis, stale material, superseded material, and unsupported gaps. | must |
| REQ-010 | The system shall provide ingestion states for draft, pending review, approved, quarantined, restricted, superseded, deprecated, and deleted items. | should |
| REQ-011 | The system shall detect and quarantine likely secrets, PII, restricted-list material, MNPI indicators, and license-restricted content during ingestion. | must |
| REQ-012 | The system shall log retrieval decisions, citations served, access denials, and answer provenance without logging confidential content unnecessarily. | must |
| REQ-013 | The system shall expose curated research to existing QuantSmith research, portfolio-management, economist, knowledge, and role-operations agents without requiring agent-specific storage integrations. | should |
| REQ-014 | The system shall support human review and canonical-source selection when multiple sources conflict. | should |
| REQ-015 | The system shall generate memory or knowledge candidates from scheduled reports and research workflows only after reviewable provenance is available. | should |
| REQ-016 | The system shall scan approved email inbox sources only for explicitly configured labels, tags, folders, or saved searches that identify market color or research. | must |
| REQ-017 | The system shall normalize tagged email market color into research items with message/thread ids, sender or publisher, sent/received timestamps, tag provenance, attachment policy, and review status. | must |
| REQ-018 | The system shall support sender/domain allowlists, deny lists, mailbox-scope limits, incremental cursors, and read-only connector permissions for email scanning. | must |
| REQ-019 | The system shall group related tagged email messages by thread while preserving each message as separately citable provenance. | should |

## Non-Functional Requirements

| ID | Requirement | Target |
| --- | --- | --- |
| NFR-001 | Access control | Unauthorized users receive no restricted content and no confirmation that restricted content exists. |
| NFR-002 | Citation coverage | 100% of answer claims derived from research items must include an accessible citation or be marked unsupported. |
| NFR-003 | Point-in-time correctness | `as_of` retrieval must exclude later-published, later-ingested, or superseding knowledge unless explicitly requested for comparison. |
| NFR-004 | Storage portability | The interface must support document stores, object storage, enterprise drives, wikis, relational metadata catalogs, and vector/search indexes behind the same MCP contract. |
| NFR-005 | Capacity | The design must support at least 1,000,000 indexed research items across asset classes without changing the agent-facing interface. |
| NFR-006 | Latency | Interactive retrieval should target p95 under 3 seconds for metadata-filtered search over approved indexes, excluding external provider outages. |
| NFR-007 | Auditability | Every ingestion, curation, access-denial, retrieval, and citation event must be reconstructable from immutable audit records. |
| NFR-008 | Compliance | The system must preserve entitlement, confidentiality, retention, deletion, and information-barrier metadata across ingestion, indexing, retrieval, and export. |
| NFR-009 | Cost control | Indexing and retrieval must support freshness windows, domain filters, tiered storage, and index compaction so stale research does not create unbounded search cost. |
| NFR-010 | Reversibility | Content deletion, deprecation, quarantine, supersession, and index rebuilds must be reversible or auditable according to retention policy. |
| NFR-011 | Email connector safety | Email scanning must be opt-in, read-only, label/tag scoped, cursor-based, and never require credentials in the SDK repository. |
| NFR-012 | Email privacy minimization | Email ingestion must avoid indexing unneeded recipients, signatures, disclaimers, calendar invites, personal content, and non-research attachments unless policy explicitly allows them. |

## Data & Dependencies

- Knowledge-base standards: `instructions/knowledge_base.md`.
- Existing knowledge-agent contracts: `agents/knowledge/knowledge_ingestion/`,
  `agents/knowledge/knowledge_curation/`, `agents/knowledge/knowledge_retrieval/`,
  and `agents/knowledge/institutional_memory/`.
- Existing source manifest template: `templates/knowledge/knowledge_sources.yml`.
- Related MCP work: `0052` resources server, `0053` memory graph server, and
  `0054` RAG server from the handoff plan.
- Related operational work: `0055` scheduled workflow operations for recurring
  research ingestion, status reports, and review reminders.
- First real runtime slice: `0059` morning market brief
  (`src/quantsmith/pipelines/market_brief.py`) builds the generated-summaries
  half of the requirement to produce candidates from scheduled reports only
  after reviewable provenance is available — proposing and staging a
  `pending_review` candidate to a local-only root, never `research/`. It does
  not satisfy this spec's access-control, quarantine, audit-logging, MCP, or
  email-connector requirements; see `0059`'s own Non-Goals.
- Data sources may include user Markdown notes, generated reports, PDFs, DOCX
  files, HTML exports, tagged email market color, email/transcript exports,
  enterprise drives, wikis, object stores, document repositories, and approved
  external research feeds.
- Required metadata includes source URI, title, author/publisher, source type,
  publication date, effective date if available, ingestion date, hash/version,
  asset class, instruments/entities, geography/currency, strategy/theme,
  confidentiality, entitlement class, freshness policy, retention policy,
  supersession links, and review status.
- Email-specific metadata includes provider, mailbox id or alias, label/tag/folder
  scope, saved-search query id when used, thread id, message id, sent/received
  timestamps, sender/publisher, attachment policy, cursor, and review status.

## Constraints & Risks

| ID | Risk | Impact | Mitigation |
| --- | --- | --- | --- |
| RISK-001 | Restricted or licensed research leaks through shared retrieval. | Compliance incident, loss of trust, vendor breach. | Enforce caller clearance as an explicit parameter, separate indexes by access tier, and deny existence leakage. |
| RISK-002 | Post-retrieval filtering leaks restricted document existence through ranking behavior. | Unauthorized users infer sensitive themes. | Filter at index selection time by access tier and entitlement before search. |
| RISK-003 | Later research contaminates historical analysis. | Look-ahead bias in research, backtests, and model narratives. | Require `as_of` support and publication/ingestion/supersession dates. |
| RISK-004 | Generated summaries become treated as primary research. | Unsupported claims propagate. | Preserve generated synthesis as a derived source type with citations to underlying items. |
| RISK-005 | Market color becomes stale but remains persuasive. | Bad decisions from old context. | Apply freshness policies, current-context filters, and explicit stale/superseded flags. |
| RISK-006 | Overbroad ingestion stores secrets, PII, or MNPI. | Legal, privacy, and compliance exposure. | Quarantine high-risk content before indexing and require review. |
| RISK-007 | One taxonomy cannot represent all asset classes cleanly. | Poor retrieval and false confidence. | Keep a common core schema plus asset-class-specific optional fields. |
| RISK-008 | External manager or sell-side terms prohibit model indexing. | Contract breach. | Carry license/entitlement class through ingestion and allow metadata-only indexing where required. |
| RISK-009 | Email scanning captures personal, client, operational, or confidential material that is not market color. | Privacy and compliance exposure; loss of user trust. | Require explicit labels/tags/folders or saved searches, sender/domain rules, read-only scopes, and review before indexing. |
| RISK-010 | Email-derived market color loses thread context or cites a synthesis instead of the original message. | Weak provenance and misleading attribution. | Preserve thread/message ids, timestamps, sender metadata, and per-message citations; generated summaries remain derived artifacts. |

## Assumptions & Open Questions

- Assumption: QuantSmith should keep one MCP retrieval interface for agents even
  when market-research storage uses separate infrastructure.
- Assumption: Real firm and third-party research content will live outside this
  repository.
- Assumption: Market-research retrieval is allowed only after an explicit caller
  clearance and entitlement context is supplied.
- Assumption: Generated research summaries are derived artifacts, not canonical
  primary sources.
- Assumption: Email market color is opt-in and tag-driven; users or firm policy
  decide which labels/folders/saved searches identify research-worthy color.
- Open question: Which enterprise stores are the first deployment targets
  (SharePoint, Google Drive, S3/object storage, Confluence, document warehouse,
  vendor research feed, or a dedicated research lake)?
- Open question: Which compliance taxonomy should be authoritative for
  confidentiality, MNPI, restricted-list, and license classes?
- Open question: Should fund-manager letters be indexed at passage level,
  metadata-only, or not indexed unless vendor terms explicitly allow it?
- Open question: Who approves canonical-source decisions when investment views
  conflict across desk, firm, and external-manager research?
- Open question: What retention and deletion policy applies to stale market
  color, generated summaries, and third-party research?
- Open question: Which email providers and labels should be supported first
  (for example Gmail labels, Outlook categories/folders, or firm mailbox saved
  searches)?
- Open question: Should email recipients be stored, hashed, omitted, or stored
  only for approved distribution-list/source attribution cases?

## Reference implementation (not a satisfied requirement)

A small, fictional-content-only reference store exists at `research/`
(`research/manifest.yaml`, `research/market_research/index.yaml`,
`research/README.md`), read by
`src/quantsmith/knowledge_console/research.py` and rendered by a Research view
in `apps/knowledge-console` (the terminal app from `specs/0057`). It exists so
that front end has real, filterable, citable data — asset class, source type,
access level, review status, provenance, supersession — to render while this
spec is Draft.

**It does not satisfy this spec's requirements** and no `REQ-*`/`AC-*` above
should be read as covered by it. Specifically absent: the knowledge-base MCP
interface / `knowledge://market_research/...` namespace (REQ-002/003),
entitlement and information-barrier enforcement before retrieval
(REQ-006, NFR-001, NFR-008), real secret/PII/MNPI quarantine detection
(REQ-011 — `review_status: quarantined` items are hand-labeled, not detected),
an email connector (REQ-016–019), and audit logging (REQ-012, NFR-007). Every
item in the store is fictional; real firm, client, fund-manager, MNPI, or
licensed content must never be committed there, per this spec's own Non-Goals.
Status remains **Draft**.
